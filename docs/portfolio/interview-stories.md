# 면접용 대표 답변 정리

> 목적: 오픈소스 기여 경험을 백엔드 개발자 면접 답변으로 바로 연결하기 위한 공개 요약입니다.

---

## 1. 오픈소스에 기여한 이유

> 실제 프로덕션 코드와 문서를 읽고, 제가 작성한 변경이 실무 수준의 리뷰를 통과할 수 있는지 검증해 보고 싶었습니다. 지금까지 Spring/Java 생태계에 총 22개의 PR을 제출했고, 3개가 머지되었습니다. 단순히 PR 수를 늘리는 것보다 어떤 문제는 왜 머지되고 어떤 문제는 왜 닫히는지 분석하면서, 문제 정의와 변경 범위를 더 정교하게 잡는 법을 배웠습니다.

---

## 2. 가장 의미 있었던 기여

Spring Boot `#49582`입니다.

`spring-boot-mail`이 클래스패스에 있어도 필수 설정이 없으면 `MailSender` bean이 만들어지지 않는데, 기존 failure analysis는 사용자를 bean 직접 정의 쪽으로 잘못 안내하고 있었습니다.

저는 이 문제를 일반 missing bean 이슈로 넓히지 않고, mail auto-configuration 조건 불일치라는 실제 원인에 맞춰 `spring-boot-mail` 모듈 안에 전용 `FailureAnalyzer`를 추가했습니다. 이후 targeted test로 `spring.mail.host`와 `spring.mail.jndi-name`이 모두 없을 때만 새 분석이 동작하도록 검증했고, PR은 2026년 3월 13일에 머지되었습니다.

---

## 3. 실패한 PR에서 배운 점

초기에는 코드가 맞으면 PR도 받아들여질 것이라고 생각했습니다. 하지만 종료된 PR을 보면 실제 원인은 코드 품질만이 아니었습니다.

- assignee가 이미 있는 이슈에 먼저 PR을 열었습니다.
- maintainer가 아직 triage하지 않은 behavior change를 구현했습니다.
- 문서 문제처럼 보여도 실제 수정 지점이 공통 템플릿인 경우를 놓쳤습니다.

이후에는 이슈 상태, 라벨, assignee, 최신 maintainer 코멘트, 기존 PR 여부를 먼저 확인하는 readiness gate를 만들었습니다.

## 4. Spring Boot 사례 꼬리질문 답변

### 왜 공통 failure analyzer를 고치지 않았나요?

> 문제 범위가 모든 missing bean이 아니라 `spring-boot-mail`의 auto-configuration 조건과 안내 메시지 사이의 불일치였기 때문입니다. 공통 로직을 바꾸면 다른 모듈까지 영향을 줄 수 있어, mail 모듈 내부의 전용 analyzer로 좁히는 편이 더 안전하다고 판단했습니다.

### 이 PR의 핵심 리스크는 무엇이었나요?

> 새 analyzer가 너무 넓게 동작해서 다른 missing bean 상황까지 잘못 설명하는 것이었습니다. 그래서 `spring.mail.host`와 `spring.mail.jndi-name` 조건을 기준으로 analyzer가 개입해야 하는 경우와 개입하면 안 되는 경우를 테스트로 나눴습니다.

### 이 경험을 실무에 어떻게 적용하겠나요?

> 공통 예외 처리나 공통 진단 로직을 바로 고치기 전에, 문제가 특정 모듈의 조건 불일치인지 먼저 확인하겠습니다. 영향 범위를 줄일 수 있다면 공통 로직 변경보다 모듈 전용 해결책을 먼저 검토하겠습니다.

## 5. Spring Data Redis 사례 꼬리질문 답변

### 왜 바로 삭제하지 않고 deprecated 처리했나요?

> `StringToPropertiesConverter`가 public class라 외부 코드에서 직접 참조될 수 있기 때문입니다. 바로 삭제하면 기존 사용자 코드가 컴파일 단계에서 깨질 수 있어, 먼저 deprecated 처리하고 내부 구현만 공통 메서드로 위임하는 방식이 더 안전하다고 봤습니다.

### 이 PR은 기능 추가가 아닌데 어떤 의미가 있나요?

> 실무에서는 새 기능을 만드는 것만큼 기존 API를 깨지 않고 내부 중복을 줄이는 작업도 중요합니다. 이 사례는 public API 호환성, 중복 구현 제거, 회귀 테스트를 함께 고려한 유지보수형 리팩터링입니다.

### targeted test만 실행한 이유는 무엇인가요?

> 변경 범위가 Redis 서버 연동이 아니라 문자열을 `Properties`로 변환하는 converter에 한정되어 있었습니다. 그래서 관련 단위 테스트인 `ConvertersUnitTests`가 변경 리스크를 가장 직접적으로 검증한다고 판단했습니다.

## 6. 실무에 적용할 수 있는 점

1. 장애나 에러 메시지를 볼 때 증상과 실제 원인을 분리합니다.
2. 기존 코드 패턴을 먼저 읽고, 변경 범위를 작게 잡습니다.
3. 기능 구현뿐 아니라 테스트, 문서, 리뷰어 설득까지 하나의 작업으로 봅니다.
4. 잘못된 시도는 숨기지 않고 회고와 운영 기준으로 바꿉니다.
